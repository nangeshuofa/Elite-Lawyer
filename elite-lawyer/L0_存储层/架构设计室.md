# 架构设计室 — Elite-Lawyer 技能自身的设计档案

> **定位**：本文件是技能的"自我说明"——用一张架构图、一组设计哲学、一套审计与进化机制，回答"这个技能为什么长这样、如何变好"。
> **读者**：维护者（升级前必读）与想深入理解技能结构的进阶使用者。
> **效力**：设计哲学与 `SKILL.md`、`L0_存储层/架构约束.md` 一致并做理念层展开；**冲突时以 SKILL.md 与架构约束.md 为准**。

## 一、架构图

### 1. 五层总览（L0 治理面 + DA 四层执行栈）

```
┌────────────────────────────────────────────────────────────┐
│ L0 存储层 — 持久化根基 · 治理面（被所有层读写）              │
│ 存储契约 · 架构约束 · 模块注册表 · 演进指南                  │
│ 集成接口 · 领域配置 · .state/config.json（schema_version 2）│
└────────────────────────────────────────────────────────────┘
          │ 提供状态与配置（唯一允许的跨层供给）
          ▼
┌────────────────────────────────────────────────────────────┐
│ L1 内核层 — 身份与原则                                      │
│ 01_角色定位（分工铁律） · 02_执业原则（六大红线/全局优先级）  │
└────────────────────────────────────────────────────────────┘
          │
          ▼
┌────────────────────────────────────────────────────────────┐
│ L2 机制层 — 纯规则 · 运转质控                               │
│ 案件流程引擎 · 时效预警 · 知识发现 · 质量控制               │
└────────────────────────────────────────────────────────────┘
          │ 触发后引用执行
          ▼
┌────────────────────────────────────────────────────────────┐
│ L3 模块层 — 可扩展功能（6 模块）                            │
│ 案件管理 · 文书生成 · 法律检索 · 合同审核 · 客户管理 · 日程提醒│
└────────────────────────────────────────────────────────────┘
          │ 读写
          ▼
┌────────────────────────────────────────────────────────────┐
│ L4 知识库层 — 知识弹药                                      │
│ 法规库 · 案例库 · 模板库 · 裁判规则 ＋ index ＋ relations    │
│（关系织网：8 种专业关系 + 待比较/待核队列）                  │
└────────────────────────────────────────────────────────────┘
```

> 两个可扩展层：L3（功能）、L4（领域与知识）。两个稳定层：L0（契约）、L1（原则）。
> L2 是连接件：L3 引用 L2 规则执行，L2 只依 L1，不允许反向。

### 2. 典型调用数据流（以"审核这份政采合同"为例）

```
用户输入
  → SKILL.md 触发词路由表匹配「政采」组
  → L3-04 合同审核工作流（政采文件审查分支）
  → 引用 L2-04 质量控制标准（P0/P1/P2 逐条审查、风险分级）
  → 读写 L4 政采分片（法规库/政府采购法 + 需求表十查/实施计划四查）
  → L4 检索协议返回关系链与溯源（未核溯源不作独立结论）
  → 输出审核意见书（✅/⚠️/❓ 可信度分级强制标注）
  → 案件状态与时效写入 L0 .state/（供下次会话读取）
```

### 3. 层间调用规则（细则见架构约束.md）

| # | 规则 | 说明 |
|---|------|------|
| 1 | 单向依赖 | 执行链 L1→L2→L3→L4 只允许向下；L0 被所有层读写，但任何层不得反向依赖 L0 之上的层 |
| 2 | 禁止循环与越级 | L3 可"引用"L1 原则与优先级，禁止"调用执行"；禁止跨层修改规则文件 |
| 3 | 单一事实来源（SSOT） | 同一规则只在一处定义：全局优先级在 L1，质量标准在 L2，触发路由在 SKILL.md；L3 需要时引用而非复制 |
| 4 | 扩展不改核心 | 新功能进模块注册表、新领域进领域配置、新知识按 index 协议进分片——均无需改 L1/L2 |
| 5 | L0 只存契约 | 存储层不含业务规则与 AI 指令，只定义"什么状态、存哪里、怎么读写与迁移" |

## 二、设计哲学

1. **判断权归律师**。AI 做信息整理、初稿、检索、提醒等重复劳动；事实判断、法律适用、策略选择、客户沟通、最终决策留给律师。技能是数字搭档，不是决策者。
2. **准确性压倒一切**。三性平衡的排序是稳定性 > 可维护性 > 可扩展性；六大红线（保密/不伪造/不承诺/不私收/不越权/不确定明说）不可突破，宁说"未检索到"也不编造。
3. **可信度先于流畅**。✅/⚠️/❓ 三级可信度强制标注——法律输出错一个法条就是执业事故，未核验的内容不得包装成定论。
4. **单一事实来源**。一条规则只定义一次，多处引用；重复定义是版本漂移的开始（V6.3.1 修复的提醒类型重复块即此类教训）。
5. **扩展不改核心**。模块注册表、领域配置、演进指南三大扩展点，保证新能力以"登记"方式进入，而不是改写内核——升级成本恒定，旧数据不失效。
6. **状态落盘可迁移**。AI 无持久内存，一切跨会话状态落地为文件；schema_version + 迁移规则承诺旧数据在新版下自动兼容。
7. **成事优先，边界不越界**。审文件是促成交易的手段：意见书结论前置、必改项≤3、能过则过；识别+量化+给选项，拍板权留给决策的人——不做拿锤子的人。

## 三、审计与进化

### 1. 审计机制

| 机制 | 做法 | 近期实例 |
|------|------|----------|
| **对照分析评测** | 拿真实任务对照测试，按 P0/P1/P2 分级修复 | 2026-09-11 评估驱动：修复提醒类型重复块（P0）、只读环境降级缺失（P0）、政采链路索引未登记（P1）→ V6.3.1 |
| **结构审计** | 版本号三处一致（SKILL.md / CHANGELOG / 文件索引）；触发词路由表、模块注册表、领域配置、config.json 四处登记对齐；schema_version 一致 | V6.3.1 政采链路"全线打通"即为一次结构审计 |
| **输出抽检** | `examples/冒烟测试对话.md` 回归；可信度分级标注抽查；知识卡指纹与溯源抽查 | 关系织网核验分级：AI 核验关系降半档，conflicts/revises 须人工确认 |

发现的问题一律分级（P0 立即修 / P1 排期修 / P2 记入路线表），修复随下一个版本发布，不为单点问题临时发版。

### 2. 进化机制

- **版本语义**：主版本=架构层变更；次版本=新增能力（向后兼容）；修版本=内容修正。SKILL.md 只保留最近版本，完整历史在根目录 `CHANGELOG.md`。
- **进化来源优先级**：办案真实反馈 > 结构审计发现 > 评测分析结论 > 前瞻学习。不为升级而升级。
- **升级纪律**：变更前过"三性平衡检查表"（架构约束.md 第五节）；升级不破坏 `.state/` 兼容；每次升级完成三处登记（SKILL.md 版本历史、CHANGELOG.md、文件索引）。
- **不做的事**：不堆没人问的模块；L3 不直接改 L2 规则（走"提议→更新 L2→L3 引用"）；知识库空结果不编造兜底；外部集成默认关闭、启用需显式配置。
