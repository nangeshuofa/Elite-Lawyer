# 演进指南 — 如何持续演进本技能

> 本文件指导维护者进行三类演进操作：**升级版本**、**迁移数据**、**扩展能力**。
> 核心原则：每次演进都必须通过 `架构约束.md` 的三性平衡检查（稳定性 > 可维护性 > 可扩展性）。

---

## 一、版本升级流程

```
Step 1 — 确定版本号（语义化：主.次.修）
  - 主版本（V6→V7）：架构层变更（如新增/删除层级、改变依赖方向）
  - 次版本（V6.0→V6.1）：新增能力（新模块/新领域/新机制），向后兼容
  - 修版本（V6.0.1）：内容修正（错别字、知识更新、提示优化）
Step 2 — 更新 SKILL.md 头部版本号（frontmatter version + 标题行）+ 版本历史段
Step 3 — 如涉及 schema 变更 → 见第二节数据迁移
Step 4 — 更新 CHANGELOG.md（新增条目；废弃版本须留痕、编号不复用）
Step 5 — 更新 README.md 版本说明
Step 6 — 重新打包 .skill 文件（testzip 验证）
Step 7 — 提交 + 推送 + 打 Release 标签（如 v6.0）
```

> ⚠️ V6.4.1 修订：原流程缺 CHANGELOG 步骤，导致版本链记录断层——已补 Step 4。

## 二、数据迁移流程（schema 变更时）

```
Step 1 — 在 存储契约.md「Schema 版本记录」表追加新版本行
Step 2 — 定义迁移规则：旧字段 → 新字段映射（或默认值）
Step 3 — 编写迁移说明（本文件对应版本段），供手动/自动迁移参考
Step 4 — 兼容性测试：用旧版 .state/ 数据在新版技能下运行，确认不报错
```

### 迁移示例（V5.2 → V6.0）
- 旧 config.json 无 `schema_version`/`domains`/`extensions` → 新版读取时补默认值
- 旧 meta.json 无 `schema_version` → 视为 v1，正常读取
- 无破坏性变更，无需人工迁移

### 迁移示例（V6.0 → V6.1）
- `schema_version` 仍为 2，**无结构变更**
- config.json 新增可选字段 `mcp_sources`/`integrations`（默认 `enabled=false`）；旧版缺失这些字段时正常读取，不报错
- 新增 `L0_存储层/集成接口.md`（外部集成扩展点规范）；旧版无此文件不影响运行
- 纯能力预留，技能行为与 V6.0 完全一致，**无需人工迁移**

## 三、扩展能力流程

### A. 新增功能模块
```
参考 模块注册表.md「新增模块规范」
1. 注册表登记 → 2. 创建 L3 模块文件 → 3. SKILL.md 路由登记 → 4. 知识库分片（如需要）
```

### B. 新增业务领域
```
参考 领域配置.md「新增领域流程」
1. 领域配置登记 → 2. 创建 L4 分片 → 3. index.md 登记 → 4. 时效/模板适配 → 5. config.json 启用
```

### C. 新增知识内容
```
1. 按 L4_知识库层/index.md 协议：定位分片 → Edit 追加卡片 → 同步 index
2. 写入前 grep 查重，避免重复
```

### D. 新增时效类型
```
1. 在 L2_机制层/02_时效预警机制.md 时效类型表追加行
2. 定义提前提醒天数 + 预警级别
```

## 四、演进检查清单（提交前自检）

| 检查项 | 必须 |
|--------|------|
| 单向依赖未被破坏 | ✅ |
| 无重复定义（Single Source of Truth） | ✅ |
| 旧版 .state/ 数据仍可读取 | ✅ |
| 新增输出均有可信度标注 | ✅ |
| 异常分支覆盖（信息不全/无果/不可用） | ✅ |
| 扩展点有对应规范文档 | ✅ |
| README + SKILL.md 版本号同步 | ✅ |

---

## 五、不兼容变更处理（Breaking Change）

当必须做破坏性变更（如删除层级、改 schema 结构）时：
1. 主版本号 +1（V6→V7）
2. 提供完整迁移脚本/说明
3. 在 Release Notes 明确标注"破坏性变更"及迁移步骤
4. 保留旧版数据读取的兼容窗口（至少 1 个主版本）

## 六、版本回滚流程（V6.4.1 新增）

> **核心规则：回滚须过结构审计**（架构约束.md 禁止项第 7 条）。回滚不是"把文件改回去"，而是受控的版本演进操作——没有审计的回滚会制造版本链暗洞（V6.5 废弃事件的教训）。

```
Step 1 — 结构审计（回滚前，全部通过才可执行）
  ① 明确回滚目标版本与范围（哪些文件、回滚到哪个 commit/版本）
  ② 检查目标版本与当前版本之间是否有第三方修改，逐文件比对，防误伤
  ③ 确认术语/专有名词等保护清单（如"律师函/律师费"不得被机械替换波及）
Step 2 — 执行回滚（逐文件替换或按历史 commit 恢复）
Step 3 — 回滚后复验
  ① 版本号三方一致：SKILL.md 头部 = CHANGELOG 最新条目 = README
  ② grep 校验：回滚目标词清零、保护术语完好
  ③ 重新打包 .skill 并 testzip，抽查关键文件头部
Step 4 — 留痕登记
  ① CHANGELOG 记录废弃/回滚说明——废弃版本号留痕且不复用
  ② SKILL.md 版本历史 + README 版本号同步
  ③ 推送 GitHub（逐文件 sha256 复验）
  ④ 重大回滚同步登记至 架构设计室.md「审计与进化」路线表
```

> 版本号规则：**已发布版本号永不复用**；未发布即废弃的版本号同样跳过（在 CHANGELOG 留痕），下一个版本顺延编号。
